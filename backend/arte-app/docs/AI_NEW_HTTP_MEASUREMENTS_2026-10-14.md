## 各点的证据、原因与改法

### 1. 初次授权是 HTTP 的大段成本，旧 Service 指标明显低估

**证据：** `getConversation` 示例 trace `ef63d18cf1f744d88b9ce08c25c68515`，Servlet 全程 1002.143ms，Factory 初次授权
801.211ms，会话 Service 的原 `elapsedMs` 仅 143ms。见 [代表 trace](measurements/2026-10-14/representative-trace.json)
。普通接口单请求授权中位约 789–920ms。

**原因：** Controller 进入会话 Service 之前，已执行身份解析、公共空间事实读取和工作空间 AI 配置读取。此前只观察 Service
会漏掉这一段，不能与浏览器总耗时等同。

**改法：** 本次已补齐 MVC 入口到 ASYNC 完成的 `AI_HTTP_METRICS`、Factory 初次授权指标和跨数据库线程 trace。后续以客户端
TTFB／total 加同 trace 的 Servlet 指标判断性能，保留 Service 指标作为内部阶段。

### 2. 身份链仍有重复数据库读取，授权快照还未消除这部分

**证据：** 上述同一请求的带 trace MyBatis 模板包含 4 次 `arte_rbac_user` 读取：按 ID、按名称、按 ID、按 ID。实际 JDBC 总数为
17，MyBatis 模板仅覆盖其中 11 次，直接 JDBC 身份映射等也已经由新指标计入。代表 trace 的 SQL 模板和线程名均已保存，不含参数。

**原因：** 认证过滤器核验账户；`RbacIdentityProvider.resolveAuthenticatedName` 再按名称读账户，`resolve` 验证映射后调用
`principal` 再读账户；公共授权还需要验证主体状态与关联。`matchesAccount` 也单独读取账户创建时间。此前合并的治理快照没有合并这些身份核验。

**改法：** 优先将账户与不可变映射核验合成一次读取，并在同一次 HTTP
操作中显式传递已验证身份事实，避免同操作重复查账户。必须保留账户主键、创建时间、名称、状态和映射退休校验；写门控和 SSE
后续重新授权仍按其一致性要求重新读取，不使用跨请求身份缓存替代撤权检查。

代码位置：`RbacIdentityProvider` 的 `resolveAuthenticatedName`、`resolve`、`principal`；
`JdbcPrincipalIdentityStore.matchesAccount`；`DatabaseAiControlService.readSnapshot`。

### 3. 很多串行 SQL 的固定往返成本，单请求也会慢

**证据：** 普通接口每次实际执行 17–21 条 SQL，单请求 SQL 执行累计 603–738ms。额外只读基线在同一 JDBC 连接执行 20 次
`SELECT 1`：中位 34.040ms，P95 34.688ms，最小 33.467ms，见 [JDBC 往返基线](measurements/2026-10-14/jdbc-roundtrip.json)
。配置及状态接口并发时 SQL 累计基本没有增加，但 HTTP 总时间显著增加。

**原因：** 即使查询计算很轻，每次数据库往返也已有约 34ms 的实测下限；十几次串行读取会累计数百毫秒。这个基线包含驱动、传输和数据库处理，不能单独证明网络延迟或某条
SQL 执行计划差。

**改法：** 先减少往返：合并重复身份查询；按 scope
批量取授权事实；沿现有批量快照读取多条调用，减少状态／结果分别请求。随后评估应用与数据库的部署距离、事务次数及结果解码。对新的慢查询异常再取得执行计划，当前数据不足以把主因归为缺索引。

### 4. 4 线程数据库调度器使 8 并发产生持续排队

**证据：** `backend/profile/app.properties` 配置 `arte.ai-new.persistence.threads=4`，`queued-tasks=256`。8 并发时普通接口排队累计中位约
850–1182ms，单请求仅 0.13–0.34ms；SQL 执行累计大多接近单请求值。`getInvocationStatus` 总耗时从 1347ms 增至 2419ms，排队中位
1133ms。

**原因：** 认证快照和业务 JDBC 工作共享有限的 `arte-ainew-db` 调度器；每个任务占用线程期间等待多次数据库往返，8 个请求争用
4 个线程。长队列可以接纳任务，但不会降低等待。

**改法：** 首先减少每任务 SQL 和事务工作。然后在与 Druid 上限、其他事务使用者及数据库容量匹配的条件下，试验 4→8
线程并复测；不能只把队列容量调大。必要时为读请求提供独立容量，避免写门控或后台任务与交互读取互相挤占。本次没有修改这些业务容量设置。

### 5. 轮次分页的只读操作仍锁定会话，并发产生锁竞争证据

**证据：** 普通读请求只有 `queryTurnsOfConversation` 的 `forUpdateExecuteMs` 非零；其单请求中位 35.570ms，并发中位
147.787ms，最大 267.584ms。`MybatisExecutionPersistence.listTurns` 明确调用 `conversationSnapshot(key, true)`
，在同一事务中核对版本、统计并分页读取。最终单请求组 InnoDB 锁等待增量为 0；并发组全局新增 33 次、累计 4235ms。第一次完整测量也为
33 次、4579ms，见两轮锁原始文件。

**原因：** 多个读操作访问同一会话行时，排他的 `FOR UPDATE` 将它们串行化。当前设计是用会话锁保证预期版本与分页期间不能插入新轮次。

**改法：** 评估将分页一致性改为只读事务的一致性快照，让版本核对、总数和页记录来自同一快照。若接口必须核验最新已提交版本，设计短暂的版本校验／重试；先明确并发写入下的契约，补充读写并发测试后再移除行锁，不能直接删
`FOR UPDATE`。

**归因限制：** `@@performance_schema=false`，`information_schema.innodb_trx` 查询权限不足（SQLState `42000`
），等待连接采样不可用，成功采样数是 0。全局计数器可能含其他服务活动；33 次／4235ms不能宣称全为本账号请求的精确等待。本报告同时保留可验证的本请求锁语句耗时，
`lockWaitMs` 仍为 null，没有把未知填成零，也没有把 `forUpdateExecuteMs` 误叫锁等待。

### 6. 连接获取有并发初期尖峰，随后没有持续饱和证据

**证据：** 并发配置读取的第一轮 8 个请求，连接获取累计中位 347.202ms、最大 867.641ms；第五轮中位 0.021ms。后续其他接口连接获取中位约
0.02–0.04ms。所有请求没有连接取得错误。项目 Druid 上限为 10、min-idle 为 5。

**原因：** 单请求预热没有覆盖 8 请求下的池需求；并发初期出现连接取得等待，而阶段总量暂不能拆出池等待与物理建连。不能只看全组中位数而遗漏第一轮尖峰，也不能据此认定稳态连接池一直不足。

**改法：** 对交互高峰提前建立所需连接，追加 Druid
active／idle／waitThreadCount、物理建连耗时来验证原因。调整数据库调度线程时同时核对池容量。后续对比建议分别报告首次并发和已预热稳态，不把二者混合解释。

### 7. SSE 必须区分首字节与连接结束

**证据：** 已完成调用 `watchInvocation` 的 HTTP 200、curl 正常结束：TTFB 1270.884ms，完整流 3498.423ms，2881 字节；服务端首写
1270.060ms、全程 3497.240ms，50 条 SQL、执行累计 1888.429ms、初次授权 822.616ms。见 `results.json` 的 `sse` 样本。

**原因：** 首帧、事件重放、结果／预算核验和关闭连接是不同时间点。长连接面板显示一分钟，可能表示订阅存活时间，不能直接说明第一帧等一分钟。本次只读已有终态调用，没有重现原活跃模型调用的一分钟连接。SSE
每 10 秒的任务是重新授权，不是状态轮询。

**改法：** 前端诊断分别记录连接首帧、首个内容增量、结果到达和连接结束；后端继续保持 SSE 体订阅的 trace。终态重放仍有 50 条
SQL，可进一步用同一次事件读取的可信状态／结果／预算事实合并重复读；每次唤醒和定时撤权检查不能用永久授权缓存跳过。

### 8. 批量读取已经减少重复入口成本，但授权仍占大头

**证据：** `getInvocationSnapshots` 当前参数的一次请求总 SQL 为 20；分别读取一个调用的状态与结果是 21 + 18 = 39
条，并各做一次工厂授权。批量接口单请求 1356ms，初次授权 789ms。该比较是实际请求 SQL 数，批量载荷以本轮固定已有 ID
集合为准，不能据此保证任意批量大小耗时相同。

**原因：** 每个 HTTP 请求都有身份／治理入口成本；前端逐调用散发状态、结果请求会重复支付这一段。批量后仍需保留一次授权及归属、结果摘要校验。

**改法：** 继续沿现有批量快照、相同资源在途合并与通知协调路径读取，避免又恢复逐个状态／结果刷新；优先优化上述一次授权中的重复身份读取。
