## 模型配置的四个页签

`/Environment/Models` 与 `/AI/Models` 使用同一模型配置页面，包含“模型管理”“租户模型与授权”“审核连接”“审核模型与费率”四个页签。
原跳转按钮由页签替代，不再在三个独立页面之间整页跳转。

- 页面顶部是空间下拉框，复用公共空间目录、当前选择及切换授权；支持继续加载，完整管理通过下拉框内“管理工作空间”进入
  `/Environment/Workspaces`。
- 模型与租户授权组件按账号和管理空间隔离；切换空间重新装配对应的读取、详情和恢复上下文。
- 审核连接及模型费率组件只按账号隔离，不按空间重建。它们仍检查原平台配置权限，空间切换不清除平台草稿或待确认命令。
- 页签按需首次挂载，打开后保持挂载；普通用户可独立使用已获授权的能力，某个平台页签权限不足不阻断其他页签。
- 模型和授权页签的未保存内容、临时密钥、待确认命令或恢复故障阻止空间切换。 平台页签的草稿允许跨空间保留；任一页签未完成处理时，“返回聊天”和“管理工作空间”跳转被阻止。
- “返回聊天”保留原 `history.push('/AI/ChatNew')` 行为，沿用应用顶部 Tab 逻辑。
- 各管理组件的保存、版本、恢复和授权机制继续复用。更新平台连接或方案后，模型详情使用“重新读取模型”显式重读，不自动覆盖已有草稿、发布或预算。

旧地址继续兼容，直接展示同一整合页面的指定页签，无须刷新跳转：

## 租户与空间政策的选择方式

租户配置顶部提供“选择租户”下拉框及“我的个人租户政策”快捷入口。 租户选项从独立读取、无搜索过滤的可访问空间目录归纳，不复用其他页面的目录搜索词；保留当前已经核验的空间作为候选。
目录按游标继续加载，不把一页或空页当作完整目录；没有可访问空间的租户不出现在候选中。 没有受权名称的租户显示其
ID，名称只采用政策接口返回的受权信息，不额外批量探测租户政策。

“租户政策”仅以 tenantId 读取、恢复及保存；“空间政策”页签内通过下拉框选择当前租户下的空间，仍按完整 scope 查询和保存。
同租户空间切换不重建租户编辑器；两个页签分别读取权限，租户政策无权读取不阻止空间负责人编辑空间政策。
切换仍经过既有公共空间选择服务重新核验，并沿用当前标签的公共空间选择和最近访问偏好规则。

完整空间管理面板已从政策页移除。“前往工作空间配置”承载原目录、创建、改名、描述和个人偏好操作；原自动初始化逻辑不变。
“前往工作空间配置”和“前往模型配置”分别通过 `history.push` 进入 `/Environment/Workspaces`、`/Environment/Models`
，沿用点击左侧菜单时的应用顶部 Tab 逻辑，不整页刷新。
政策草稿、待确认命令、恢复故障或提交中的操作会阻止租户和空间切换；有政策草稿或待确认政策操作时也不能跳转其他配置页。
原按账号／租户／空间隔离的恢复键保持兼容，不会自动重发待确认命令。政策保存后仍需显式刷新、核对与应用相应业务配置。

租户与空间政策选择方式调整只修改前端与文档，无新增接口、RBAC 权限编码、菜单脚本或业务 DDL；原菜单路径和政策接口保持兼容。

## 新环境与已有环境部署

1. 部署本次前端代码。后端无新增接口、配置项或业务 DDL；登录、公共平台及对应模型／工具开关和既有表仍须满足原要求。
2. 新环境执行 RBAC 基线 `scripts/arte-rbac-dml-mysql.sql`，已包含本次菜单定义；已有环境在目标应用库（如 `arte`）执行
   [`scripts/arte-environment-menu-dml-mysql.sql`](../scripts/arte-environment-menu-dml-mysql.sql)
   。执行前暂停并发菜单维护，核对同编码／路径冲突。
3. 脚本按自增 ID 新增顶级菜单及四个子菜单；可以复用此前手工登记的 `Environment`、`/Environment` 顶级菜单。
   同编码或同路径的已有菜单（包括停用状态）不覆盖、不重新启用；异常父级或冲突记录不会被自动修复。
4. 脚本仅向已存在且启用的 `admin` 角色分配五个菜单，不向用户或角色增加业务动作权限，也不修改原 `aiModels`、`aiTool`、
   `ChatNew` 等菜单。 其他管理角色或仅有直接用户授权的账号，通过现有菜单分配页面分配 `Environment` 及需要的子菜单。
5. 在“角色管理”中查看受影响角色的详情，触发数据库重读并刷新角色缓存，然后重新加载当前登录信息和页面。 使用受权 API 时可调用
   `POST /arte/rbac/role/getRoleByCode`，请求体为 `{"roleCode":"admin"}`，要求现有 `role:list` 权限。
   如还调整了用户直接绑定菜单，应通过用户管理刷新该用户权限。不要通过清空全部 Redis 来刷新菜单。

前端同时根据父菜单和子菜单的权限展示导航。只分配父菜单不会自动授予四个子菜单；环境配置首页也只展示已分配的入口。 菜单关系由
SQL 更新后，Redis 中原用户／角色权限缓存仍可能存在；单纯重启应用或重新登录不保证刷新这些缓存。

## 验证与排查

1. 检查 `arte_rbac_menu` 中五个编码的路径、启用状态、展示标记，以及子菜单的 `father_id` 是否指向唯一的 `Environment` 顶级菜单。
2. 检查 `arte_rbac_relation` 中目标角色的五条 `role_to_menu` 关系。
3. 刷新权限后检查 `/arte/auth/onlineInfo` 的 `menus`，应包含 `Environment` 及所分配的子菜单编码。
4. 在左侧展开“环境配置”，分别点击四个子菜单；刷新任一配置地址，确认没有 404，且未登录时仍走原登录保护。
5. 检查菜单及顶部标签的中文／英文名称。配置页中的具体操作仍按当前租户、空间、资源和凭据资格决定，菜单可见不等于可以修改资源。

没有菜单时，优先核对菜单关系与权限缓存；菜单可见但页面 404 时，核对前端版本及约定式路由；页面打开后权限不足时，按原业务资格排查。
菜单脚本可串行重复执行；不以脚本重复执行替代冲突修复。
