# 首字优化第三批：Worker 即时唤醒与持续补充槽位

## 行为变化

第三批消除了正常调度路径的整批等待和固定休眠。DISPATCH Outbox 随受理事务提交后立即发本地检查提示；自动 Worker
串行领取空闲槽位能立即执行的消息，逐条独立运行。每条完成、失败或延后处理并释放槽位后，立即请求下一次领取，其他长任务继续运行。

| 场景                         | 原有 Worker                | 本批 Worker                              |
|------------------------------|----------------------------|------------------------------------------|
| 空闲期间提交                 | 等下一次轮询，默认一秒周期 | 提交后提示驱动领取                       |
| 一批中某条完成，另一条仍运行 | 等整批全部结束，再休眠     | 完成一条后补充空出的槽位                 |
| 满载收到重复提示             | 自动循环仍等待批次         | 合并提示，满载时不发领取查询             |
| 提示遗漏或进程崩溃           | 批次结束后才进入下一次扫描 | 独立恢复定时器检查，数据库租约到期后接手 |

`pollInterval` 保留原配置及默认一秒值，语义为恢复扫描周期。扫描不等待当前所有任务结束；延后任务仍遵守数据库的到期时间，通过后续扫描或其他提示触发的领取恢复，不提前重试。恢复扫描无法突破全部槽位已占用的容量限制。

## 实现与仲裁

- `LocalDispatchNotifier` 分别提供 Worker 提示和提交广播提示。订阅先登记再发初始检查；LATEST 合并积压，不持久保存任务，也不发放发送许可。
- `MybatisExecutionPersistence` 仅在 DISPATCH Outbox 写入事务的 `afterCommit` 调用提示；回滚及幂等重放不重复通知。提示失败不改变已提交的业务结果。
- `InvocationDispatchWorker` 的自动循环只串行执行领取，按当前空闲槽位传入
  limit。每条任务继续使用既有领取续租、当前资格复查、预算、Attempt、fencing、派发事实与 ACK/延后处理路径。
- 每次启动有独立的活动计数和有界任务订阅集合，完成后移除句柄。停止取消提示监听、恢复定时器和每条任务订阅；未确认记录继续按数据库租约恢复，旧启动回调不影响新启动槽位。
- 手动 `pollOnce` 保留处理一批后返回计数的行为；自动运行或已有手动批次时返回 0。自动启动与正在运行的手动批次交错时，等待该批结束后再领取，避免叠加并发。

本地监视器仅保护调度计数与生命周期，不替代业务锁。多实例领取身份、token、租约及发送事实仍由数据库仲裁；本批没有数据库结构变更。

## 多实例提示

复用已有 `arte.ai-new-events.transport` 和通道配置。REDIS 模式下，`DispatchWakeupPublisher`
异步广播固定的检查提示；提示不含用户正文、身份或任务内容，也不阻塞受理提交。即使本机 `worker-enabled=false`，仅 HTTP
受理节点仍会广播。

远端 Worker 收到提示或 Redis 完成重新订阅后主动检查数据库，不再次广播，避免回送循环。发布失败或订阅尚未就绪时由恢复扫描兜底。

LOCAL 模式只唤醒同进程 Worker。分离 HTTP/Worker 或多实例需要即时远端唤醒时，各节点应使用 REDIS 模式、相同通道和已有
RedissonClient；本批没有修改用户当前的 LOCAL 配置。
