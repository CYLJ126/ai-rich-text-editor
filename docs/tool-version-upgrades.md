# 工具版本与稳定用户配置

用户绑定保存稳定的 bindingId、工具身份、作用域、凭据引用、用户配置和策略覆盖。版本升级不重建绑定，也不修改助手关联。

## 用户行为

- 新绑定默认跟随兼容版本；用户可以锁定版本。
- 绑定保留基准版本，调用时按已发布的兼容关系选择实际版本。页面分别显示基准版本、实际版本、更新状态。
- 兼容发布无需用户重新配置；不兼容发布只提示更新，用户在同一绑定内显式选择新版。
- 版本选择和配置修改使用同一行乐观锁，作用域和工具身份不可变。凭据与用户覆盖不会在升级时被复制或清空。
- 已生成的调用及审批任务保持其具体版本，不能在执行或恢复时悄悄切换版本。

## 管理行为

- 每个本地 @Tool 方法可通过 @ToolRelease 独立声明版本。
- 管理员发布版本时选择兼容基准、填写发布说明；服务端校验 Schema、默认配置、执行策略及风险权限。
- 兼容性由显式发布声明与服务端检查共同确认，不依据版本号大小猜测。
- 兼容链支持连续升级。禁用和废弃的版本不可作为实际执行版本。
- Spring AI 本地工具可以以已验证兼容的新执行器承接旧版本契约，旧版本的风险、策略、Schema
  快照保持不变。无法兼容的执行器需要同时提供旧实现，不能仅靠数据库快照伪装旧实现。

## 数据迁移

新增 binding.version_policy（follow-compatible /
pinned）、version.compatibility_base_version、version.release_notes。已有绑定默认跟随经过显式确认的兼容版本；没有发布兼容关系前，实际执行版本保持原基准。

发布新版本不会修改用户配置、凭据或助手关系。数据库迁移仅新增版本管理字段，不自动发布草稿。

## 本地工具声明示例

```java
import com.arte.ai.common.annotation.ToolRelease;
import com.arte.ai.common.annotation.ToolRisk;
import com.arte.ai.common.enums.tool.ToolRiskLevelEnum;
import org.springframework.ai.tool.annotation.Tool;
import org.springframework.ai.mcp.annotation.McpToolParam;

@Tool(name = "random-name", description = "Generate a random name")
@ToolRelease(version = "1.0.1", compatibleWith = {"1.0.0"})
@ToolRisk(readOnly = true, level = ToolRiskLevelEnum.LOW)
public String randomNameForTool(@McpToolParam(description = "First name") String firstName) {
    // 在 ArteMcpTools 中保留原实现；此处省略日志。
    return lastNameList.get(ThreadLocalRandom.current().nextInt(lastNameList.size())) + firstName;
}
```

`ToolRelease.version` 优先于 `arte.ai.tool.local.version`，因此一个方法发新版本不会改变其他已经独立声明版本的方法。未声明的方法沿用提供者全局版本；程序式
ToolCallback 可构造带 compatibleVersions 的 SpringAiToolAdapter。原生 Tool 可以在提供者中同时注册多个精确版本。

`compatibleWith`
是开发者对执行器行为兼容的承诺，用于部署新版代码后继续承接已发布的旧契约。它不会自动发布新版，也不会让用户绑定提前选择草稿。服务端仍检查真实运行时定义与数据库快照一致，以及旧版与新版契约兼容。检查无法证明代码业务行为，开发者仍需验证业务语义。

“锁定版本”锁定执行契约与风险/策略快照。明确声明兼容时，旧契约可由新版实现执行；如果要求锁定原始实现，应保留独立的原生旧版本
Tool。无法兼容的更新也必须同时保留旧版实现，或先明确迁移用户，再停用旧版。

## 发布与升级操作

1. 部署前执行 `backend/arte-ai/scripts/arte-ai-tool-ddl-mysql-3.sql`。新环境按 1、2、3 的顺序执行工具建表脚本。本次开发库已添加这三个字段，无需重复执行迁移。
2. 修改方法自己的版本号，保留真实的兼容声明，重新构建并重启后端。在“工具提供者”刷新，产生新草稿。
3. 打开“工具目录 → 新版本详情 → 发布”。选择已发布的兼容基准，填写面向用户的升级说明。页面显示契约检查结果、会自动更新的绑定数和保持锁定的绑定数。
4. 兼容检查通过并发布后，默认跟随的用户无需操作。绑定列表显示实际版本及原基准；用户配置、凭据引用、审批覆盖、绑定 ID
   和助手关联保持不变。
5. 不兼容版本采用“独立发布”。用户在“用户绑定 → 配置 / 查看更新”查看说明，选择新基准版本，并按需调整配置，在原绑定内保存。助手无需重新选择绑定。
6. 需要固定契约的用户选择“锁定所选版本”。禁用或废弃该版本会使锁定绑定不可用，不应在仍有锁定用户时直接下架。跟随绑定只有存在其他已发布且可执行的兼容版本时才能继续调用。

当前运行库中 `name-assessment` 和 `random-name` 的 `1.0.1` 均已发布。重新启动后，在各自 `1.0.1` 详情中点击“设置兼容升级”，以
`1.0.0` 为基准填写说明并确认即可。对已发布版本只允许补充一次兼容关系，且基准必须更早发布；已有兼容关系不可改写，定义、校验和与原发布时间保持不变。以后发布新草稿时直接选择兼容基准。

## 执行边界

兼容检查保守地要求输入/输出 Schema、默认配置和执行能力一致；执行策略除移除默认人工审批外保持一致。不得扩大作用域/网络范围、提高风险或降低只读等行为保证。有意改变这些契约的版本应独立发布。

版本解析只选择已发布、提供者启用且本节点存在可执行实现的版本；按发布时间选择，不猜测语义版本大小。兼容链可以跨越已禁用的中间版本，但被禁用的版本本身不会被选作执行版本。旧任务的明确版本授权仍须处于绑定的兼容链或锁定版本中，版本下架后不能继续执行。

运行时注册表整批替换提供者快照，校验失败保留原快照，避免刷新时先清空导致暂时不可用。版本记录与配置变更采用行版本检查，冲突不会悄悄覆盖另一份配置。

## 普通用户权限

普通用户角色分配 `aiTool:list` 与 `aiTool:invoke`，即可查看工具、配置自己的绑定和助手工具、调用工具。配置接口仍从
UserContext 获取用户身份，并检查绑定/助手归属。`aiTool:manage` 继续控制全局发布、同步和禁用，不需要为普通用户配置工具授予该权限。本次未修改现有角色授权数据。

## 工作流升级与运行版本

工作流节点保存工具契约基准版本和稳定的
bindingId。每次开始新运行时，服务端按绑定的升级方式选择实际工具版本，并验证该版本仍与工作流的契约基准兼容。兼容升级无需修改、重新保存或重新发布工作流；锁定版本的绑定继续使用锁定版本。

一次运行的全部工具版本在启动时解析并写入检查点 `resolvedTools`
，运行详情显示每个节点的实际工具版本。运行中的重试、暂停恢复和异步任务继续使用这份版本记录；后续新运行才使用新发布的兼容版本。已有检查点没有该字段时，继续使用原发布计划中的精确版本。授权或版本被撤销时执行失败，不会临时切换版本。

用户显式将绑定切换到不兼容版本后，旧工作流不能自动套用新契约，需调整对应节点的契约基准、参数或输出映射并发布新工作流版本。绑定
ID、凭据和用户配置仍保留。

工作流启动直接读取已发布计划，不重新编译。旧校验和因 Map/Set
序列化顺序变化产生的不一致不会要求用户重新发布；程序接口提交的计划仍需通过规范化定义比较，并且实际执行已发布快照。新校验和规范化集合、对象键和
Schema JSON，保留节点、边及其他列表的语义顺序。本修复不改写已发布计划或旧校验和，无需额外数据库迁移。
